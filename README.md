# Прогноз продаж по складам и товарам

Недельный прогноз продаж на 9 недель (27.07-27.09.2026) для каждой пары склада и товара: 11 складов x 799 товаров x 9 недель = 79 101 строка. Для обучения можно брать только данные по 26.07.2026.

- [notebooks/solution.ipynb](notebooks/solution.ipynb) - обзор решения с числами и графиками: как шли от наивного прогноза к финалу, что сработало и что нет.
- [submission/submission.csv](submission/submission.csv) - финальный прогноз. Контейнер по последним 180 дням данных выдаёт тот же файл байт в байт.
- Контейнер с API (раздел 10 ТЗ): `make up`, потом http://localhost:8000. Документация API на `/docs`, обзор решения на `/solution`.
- [docs/](docs/README.md) - что лежит в каждом модуле и файле, зачем он нужен и почему сделан так.

## Коротко

| | |
|---|---|
| Модель | классификатор (будет ли продажа на неделе, 40 признаков), регрессор (сколько, если будет, 38 признаков) и правило "0 или k" под метрику; ансамбль из двух CatBoost (сиды 42 и 7) и LightGBM. Состав и признаки по моделям в разделе 3 `notebooks/solution.ipynb` |
| Финал на бэктесте | score 0.8077 / 0.8194 / 0.7832 на фолдах season2025 / season2024 / recent, у v5 было 0.8091 / 0.8228 / 0.7877 (0 значит идеально, 1 значит не лучше прогноза "как на прошлой неделе") |
| Контейнер | CPU, без сети; полный прогноз по 180 дням считается ~7 с, повторный запрос отдаётся из хранилища |

## Решение

```
история по неделю T включительно -> признаки пары на неделю T (окно до 24 недель)
  классификатор: P(продажа на неделе T+h)   CatBoost x2 + LightGBM, среднее вероятностей
  регрессор: сколько, если продажа будет    CatBoost x2 + LightGBM, среднее в логарифмах (log1p)
решение: p > 0.55 на неделях 1-4 или p > 0.5 на неделях 5-9 -> целое с наименьшим ожидаемым SMAPE при q, иначе 0
```

- Почему две ступени. Половина скора - SMAPE по каждой паре-неделе, а 56 % пар-недель нулевые. Если факт 0, а прогноз 0.01, ошибка уже 200 %. Поэтому вероятность продажи и количество считают разные модели, и там, где продажи, скорее всего, не будет, ставится ровно 0.
- Признаки (`src/features.py`, таблица групп в `notebooks/solution.ipynb`): лаги и средние, частота и давность продаж, обычное количество, тренды пары, товара, склада и категории, товар на всех складах, остатки, цена и скидка, география покупок, календарь целевой недели. Окно не длиннее 24 недель: в контейнер приходят 180 дней, и прогноз по ним совпадает с прогнозом по всей истории.
- Обучение. Строка - это пара, неделя отсчёта и горизонт 1-9 (горизонт тоже признак). Вес строки равен 0.5^(возраст / 26 недель), потому что данные дрейфуют: в середине 2024 появился склад `warehouse_name_10`, категория 1_4 за год выросла на 135 %.
- Решение под метрику. Продают обычно 1-2 штуки, и дробный прогноз проигрывает целому (1.58 при факте 1 даёт SMAPE 45 %). Количество переводится в целое с наименьшим ожидаемым SMAPE, если продажи на неделе с продажей = 1 + Пуассон(q - 1). Соответствие прогноз -> целое, выученное по фактам, на сезонных фолдах было лучше, но на `recent`, ближайшем к тесту, завышало объём и ухудшало WAPE, Bias и RMSLE, поэтому в финал не вошло.
- Проверка. Три фолда с отсечкой в прошлом: season2025 (тот же сезон, что тест, главный), season2024 и recent. Идею берём, только если она не хуже на обоих сезонных фолдах, а на recent хуже не больше чем на 0.005. Метрики считаются как в `score.py` из ТЗ.

Score на главном фолде season2025 по шагам: наивный прогноз 1.000, медиана за 8 недель 0.871, первая модель 0.819, потом тренд категории, вес свежих недель, целое под SMAPE и второй CatBoost (v5, 0.809), LightGBM в ансамбле и порог по горизонту (финал, 0.808). Оракул, который знает частоту продаж пары в тесте, даёт 0.774. Всего проверили 26 идей, в модель вошли 7. Что не сработало и почему (Tweedie, множители, признаки пополнения остатка, сезонный вес, разброс продаж пары, выученное соответствие и другое) описано в `notebooks/solution.ipynb`, таблицы лежат в `results/`.

## Контейнер с API

Все файлы Docker лежат в `docker/`, образ собирается из корня репозитория. Подробно про образ и переменные окружения в [docs/docker.md](docs/docker.md), про устройство сервиса в [docs/app.md](docs/app.md).

### Сборка и запуск

Нужен Docker с BuildKit (по умолчанию начиная с Docker 23 и в Docker Desktop) и Docker Compose v2. GPU не нужен: CatBoost и LightGBM считают прогноз на CPU за секунды, поэтому образ без CUDA, около 1.05 ГБ.

```bash
make build                                    # docker build -f docker/Dockerfile -t sberhack-forecast .
docker run -p 8000:8000 sberhack-forecast     # http://localhost:8000
make up                                       # то же через docker compose, прогнозы хранятся в томе и переживают рестарт
make down
```

- Python 3.13 и версии библиотек модели в `docker/requirements.txt` (pandas, numpy, scipy, catboost, lightgbm, holidays) такие же, как при финальном обучении на Kaggle (`libraries` в `model/config.json`), поэтому прогноз контейнера совпадает с сабмитом.
- В контекст сборки попадает только нужное (белый список в `docker/Dockerfile.dockerignore`), данные организаторов (528 МБ) туда не идут.
- Флаг `--gpus` не нужен. Готовность можно проверить через `GET /ready` (~5 с после старта), в образе есть `HEALTHCHECK`. Интернет при работе не нужен: модель, документация API и обзор решения лежат внутри образа.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DOCS` | `1` | при `0` отключаются `/docs`, `/redoc`, `/solution`, `/openapi.json`, а `/` вместо стартовой страницы отдаёт короткий JSON |
| `WORKERS` | `2` | число процессов uvicorn, прогнозы у них общие через хранилище |
| `MAX_CONCURRENT_PREDICTIONS` | `1` | одновременных расчётов на процесс (полный POST берёт до ~1 ГБ памяти) |
| `MAX_FORECASTS` | `20` | сколько последних прогнозов хранить |
| `CACHE_DIR` | `/cache` | хранилище прогнозов (том в `docker/docker-compose.yml`) |
| `MODEL_DIR` | `/app/model` | папка модели, для подмены модели укажите другую |
| `ADMIN_TOKEN` | не задан | если задан, появляется `POST /model/reload` с заголовком `X-Admin-Token` |

### API

| Метод и путь | Что делает |
|---|---|
| `POST /predict` | принимает `sales` и `stock` (CSV в формате организаторов, от 180 дней), сохраняет прогноз на 9 недель и возвращает JSON с `forecast_id` и `success`; с `?return_csv=true` возвращает CSV и `X-Forecast-Id` |
| `GET /predict?article=&warehouse=` | прогноз по товару, складу или паре (нужен хотя бы один параметр) |
| `GET /predict/all?format=csv\|json` | весь прогноз, отдаётся потоком |
| `GET /explain?article=&warehouse=` | разбор прогноза по паре: вероятность и порог по неделям, сырое и целое количество, главные признаки по SHAP |
| `GET /health`, `GET /ready` | процесс жив / модель загружена (иначе 503) |
| `GET /model/info` | дата обучения, состав ансамбля, правило решения, метрики бэктеста, версии библиотек |
| `POST /model/reload` | перечитать модель без рестарта (только при заданном `ADMIN_TOKEN`) |
| `/`, `/docs`, `/redoc`, `/solution` | стартовая страница, Swagger UI, ReDoc и обзор решения; включаются флагом `DOCS`, работают без интернета |

```bash
curl -X POST http://localhost:8000/predict -F "sales=@data/sample_sales.csv" -F "stock=@data/sample_stock.csv"
# Ответ: {"forecast_id":"...","success":true}. Подставьте полученный forecast_id:
curl "http://localhost:8000/predict/all?forecast_id=..." -o forecast.csv
# Сразу получить CSV и идентификатор в заголовке X-Forecast-Id:
curl -D headers.txt -X POST "http://localhost:8000/predict?return_csv=true" -F "sales=@data/sample_sales.csv" -F "stock=@data/sample_stock.csv" -o forecast.csv
curl "http://localhost:8000/predict?article=char_article_391"                             # товар на всех складах
curl "http://localhost:8000/predict?warehouse=warehouse_name_3"                           # все товары склада
curl "http://localhost:8000/predict?article=char_article_391&warehouse=warehouse_name_3"  # одна пара
curl "http://localhost:8000/predict/all?format=csv" -o full_forecast.csv
curl "http://localhost:8000/predict/all?format=json"
curl "http://localhost:8000/explain?article=char_article_391&warehouse=warehouse_name_3"
```

В ответах с прогнозом есть заголовки `X-Forecast-Id` (id прогноза) и `X-Model-Version` (хеш файлов модели), а `POST /predict` добавляет ещё `X-Cache: hit|miss` и `Server-Timing` (время этапов). GET без `forecast_id` берёт последний прогноз, как в ТЗ, а с `forecast_id` отдаёт указанный.

Ошибки приходят в виде `{"detail": "...", "code": "..."}` (раздел 10.4 ТЗ). Если проблем несколько, добавляется список `errors`. Поля JSON-ответов и ошибок описаны pydantic-схемами в `app/schemas.py` и видны в `/docs`, полный список кодов в [docs/app.md](docs/app.md).

| Код | Когда |
|---|---|
| 400 `EMPTY_FILE` / `BAD_CSV` | пустой файл, только заголовок, не CSV |
| 400 `BAD_REQUEST` | GET без `article` и `warehouse`, `format` не csv/json |
| 422 `VALIDATION_ERROR` | нет колонок, даты не в формате `YYYY-MM-DD`, история меньше 180 дней, отрицательные `quantity`, нет файла в запросе |
| 404 `NO_FORECAST` / `NOT_FOUND` | прогноза ещё нет (сначала нужен POST) / в прогнозе нет такой пары |
| 503 `MODEL_NOT_READY` | модель не загрузилась |

Отрицательный `stock` не ошибка, это резерв. Пустой `discount_sum` значит, что скидки не было. Товар в `stock` может называться `char_article` (как в ТЗ) или `article` (как в выданных файлах).

### Как устроен сервис

- Воркеры не хранят состояние. Прогноз сохраняется в файловое хранилище (`CACHE_DIR`) с ключом из хеша версии модели и присланных файлов: повторный POST с теми же данными отдаётся сразу и совпадает байт в байт, GET работает в любом воркере и после рестарта, у каждого клиента свой `forecast_id`. В шаблоне из ТЗ прогноз лежит в памяти процесса, и при нескольких клиентах или воркерах это ломается.
- Модель спрятана за интерфейсом `ForecastModel` (`app/predictor.py`). Реализацию выбирает поле `kind` в `config.json` папки модели: `two_stage` (итоговая модель) или `baseline` (среднее за 8 недель, для сравнения). Чтобы подменить модель, достаточно указать другую папку (`MODEL_DIR`) и перезапустить сервис. `POST /model/reload` перечитывает модель из той же папки и только в том процессе, который принял запрос, так что при нескольких воркерах надёжнее рестарт.
- Код прогноза общий с обучением: сервис использует тот же `src/forecaster.py`, которым обучалась финальная модель и считался сабмит, поэтому то, что проверяли на бэктесте, и то, что отдаёт сервис, не расходятся.
- Расчёт идёт в отдельном потоке, и в каждом процессе одновременно идёт не больше `MAX_CONCURRENT_PREDICTIONS` расчётов (остальные запросы ждут). Поэтому `/health` отвечает и во время долгого POST, а много больших запросов разом не съедят память.
- Код разложен по ролям: `main.py` собирает приложение, эндпоинты лежат в `routes/`, схемы ответов в `schemas.py`, ошибки в `errors.py`, проверка входа в `validators.py`, хранилище в `store.py`.

## Данные и метрика

- В продажах есть строки только за дни с продажами, поэтому строится полная сетка пара x неделя, пропуски заполняются нулями. Продажи идут с 2024-01-01, всё позже 2026-07-26 `load_data()` отрезает, как требует ТЗ.
- `quantity` целые, почти всегда 1-2 в день. В сезоне 2025 нулевые 56 % пар-недель, обычная ненулевая неделя - 2 штуки. 5 % пар дают ~45 % объёма, а склады `warehouse_name_2` и `_3` дают почти 60 %.
- В `stock` бывает до 4 строк на день, склад и товар (суммируем). Отрицательный остаток - резерв. Около трети продаж приходится на дни с нулевым остатком (клиента предупреждают, что товара нет), так что нулевой остаток не значит, что продаж не будет.
- `sales_sum` и `discount_sum` даны логарифмами (`np.log`, по ТЗ), перед суммированием нужен `np.exp`. Пустой `discount_sum` значит, что скидки не было.
- Бизнес меняется (FAQ организаторов, п. 8): в середине 2024 появился склад `warehouse_name_10`, категории растут с разной скоростью. Поэтому признаки в основном относительные (тренды, доли), а свежие недели весят больше.
- Метрика: SMAPE 50 % (по каждой паре; факт 0 и прогноз 0 дают ошибку 0, факт 0 и прогноз 0.01 дают 200 %), WAPE 20 %, RMSE 15 %, Bias 10 % (по парам с продажами, прогноз из одних нулей даёт 100 %), RMSLE 5 %. По ТЗ итоговая нормализация ранговая, локальный `score` считается как min-max к наивному прогнозу (0 значит идеально, 1 значит не лучше прогноза "как на прошлой неделе").

## Ограничения

- На вход приходит только 180 дней. Признаки считаются по окну до 24 недель, признаков того же сезона год назад у модели нет: год истории в контейнер не приходит.
- Новые товары и склады. Прогноз строится для всех складов и товаров из присланных `sales` и `stock`, других пар в нём не будет. У пары без продаж за 24 недели прогноз почти всегда 0.
- Модель не знает будущего: акций, изменений цен и скидок на неделях прогноза. Скидки у категории 1_5 перед тестом на рекордном уровне, в обучении такого почти не было.
- Порог и правило перевода в целое подобраны на трёх фолдах, сезон 2026 может вести себя иначе.
- Обучение идёт на Kaggle GPU, локальная машина (~8 ГБ) тянет только облегчённые варианты. Обучение на GPU побитово не воспроизводится, поэтому сабмит считается из сохранённых моделей, и они лежат в репозитории.
- Хранилище прогнозов - файлы на одном хосте (том Docker). Для нескольких хостов нужно общее хранилище (S3, Redis), под это выделен класс `ForecastStore`.
- `/explain` показывает вклады признаков первой CatBoost-модели ансамбля, а не всего ансамбля. Вероятность и количество при этом считаются по всему ансамблю.
