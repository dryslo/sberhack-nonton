# app/: HTTP-сервис

Сервис по разделу 10 ТЗ на FastAPI: принимает `sales` и `stock` за последние 180+ дней, отдаёт прогноз на 9 недель и выборки из него. Файлы `main.py`, `predictor.py` и `validators.py` названы как в разделе 10.5 ТЗ, остальной код разложен по ролям.

## Как проходит запрос

```
POST /predict (sales.csv, stock.csv)
  routes/predict.py   принимает файлы, тяжёлый расчёт уводит в отдельный поток
  service.py          ключ = хеш(версия модели + оба файла)
                      прогноз с таким ключом уже есть в store.py -> отдаём его (X-Cache: hit)
                      иначе:
                        validators.py   колонки, даты, от 180 дней, продажи не отрицательные (400 / 422)
                        predictor.py    ForecastModel.predict, не больше MAX_CONCURRENT_PREDICTIONS расчётов разом
                                        two_stage -> src/forecaster.py: Panel, ансамбль, pipeline.decide
                        store.py        CSV, метаданные и данные для /explain, указатель на последний прогноз
  ответ: JSON {"forecast_id": "...", "success": true}; при ?return_csv=true — CSV
         заголовки в обоих режимах: X-Forecast-Id, X-Model-Version, X-Cache, Server-Timing

GET /predict, /predict/all, /explain
  берут из хранилища последний прогноз (или указанный forecast_id): фильтр, весь прогноз потоком, разбор по паре
```

## main.py

`create_app(settings)` собирает приложение: обработчики ошибок, маршруты, документацию по флагу `DOCS`. В `lifespan` модель загружается один раз на воркер. Если она не загрузилась, сервис всё равно поднимается: `/health` отвечает, а остальные эндпоинты отдают 503 с причиной, так что проблему видно сразу. Приложение собирается фабрикой, потому что тесты создают его с разными настройками: без документации, с токеном, с baseline-моделью. Строка `app = create_app()` в конце нужна uvicorn.

## config.py

`Settings` из переменных окружения:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `MODEL_DIR` | `model` | папка модели |
| `CACHE_DIR` | `/tmp/forecast-cache` (в образе `/cache`) | хранилище прогнозов |
| `MAX_FORECASTS` | `20` | сколько последних прогнозов хранить |
| `MAX_CONCURRENT_PREDICTIONS` | `1` | расчётов одновременно на процесс |
| `DOCS` | `1` | документация и стартовая страница |
| `ADMIN_TOKEN` | не задан | включает `POST /model/reload` |

## routes/

`POST /predict` по умолчанию возвращает JSON с `forecast_id` и `success: true` после расчёта и сохранения.
Скачать результат можно через `GET /predict/all?forecast_id=...`. Параметр запроса `return_csv=true`
возвращает CSV сразу, вместе с идентификатором в заголовке `X-Forecast-Id`. Оба режима используют одно хранилище
и один ключ кэша. Это синхронный расчёт: `success` означает, что прогноз уже сохранён, а не поставлен в очередь.

- `predict.py`: `POST /predict`, `GET /predict` (по товару, складу или паре), `GET /predict/all` (CSV или JSON), `GET /explain`. В ответах с прогнозом есть `X-Forecast-Id` и `X-Model-Version`, POST добавляет `X-Cache` и `Server-Timing` с временем этапов. JSON из `/predict/all` отдаётся потоком кусками по 5000 строк, чтобы не собирать в памяти ответ на 79 101 строку. Тяжёлые вызовы идут через `run_in_threadpool`, поэтому `/health` отвечает и во время долгого расчёта.
- `system.py`: `/health` (процесс жив), `/ready` (модель загружена), `/model/info` (дата обучения, состав ансамбля, правило решения, метрики бэктеста, версии библиотек), `/model/reload`. Перезагрузка подключается, только если задан `ADMIN_TOKEN`, и проверяет заголовок `X-Admin-Token`. Модель она перечитывает из той же папки и только в том воркере, который принял запрос, поэтому при нескольких воркерах надёжнее рестарт.
- `docs.py`: `/docs` (Swagger UI), `/redoc`, `/solution` (обзор решения) и стартовая страница `/`. Скрипты Swagger UI и ReDoc отдаются из `app/static`, а не с CDN: у контейнера может не быть интернета. При `DOCS=0` всё это отключается, а `/` отдаёт короткий JSON со списком эндпоинтов.

## schemas.py

pydantic-схемы JSON-ответов и ошибок. По ним FastAPI проверяет ответы и строит `/docs`, поэтому в документации видны поля каждого ответа и формат ошибки для каждого кода. Входные CSV схемами не проверяются: построчно на сотнях тысяч строк это слишком медленно, таблицы целиком проверяет `validators.py`. `ModelInfo` пропускает лишние поля, потому что у разных моделей описание разное.

## errors.py

Все ошибки отдаются в одном формате по разделу 10.4 ТЗ: `{"detail": "...", "code": "..."}`, если проблем несколько, ещё список `errors`. Сюда же сведены ошибки самого FastAPI (неверный запрос, 404 на неизвестный путь, 405), чтобы клиент никогда не получал другой формат.

| Код | Когда |
|---|---|
| 400 `EMPTY_FILE` / `BAD_CSV` | пустой файл, только заголовок, не CSV |
| 400 `BAD_REQUEST` | GET без `article` и `warehouse`, неверный `format` |
| 403 `FORBIDDEN` | неверный `X-Admin-Token` |
| 404 `NO_FORECAST` / `NOT_FOUND` | прогноза ещё нет / в прогнозе нет такой пары |
| 409 `MODEL_CHANGED` | `/explain` по прогнозу, который сделала другая версия модели |
| 422 `VALIDATION_ERROR` | данные не прошли проверку или в запросе нет файла |
| 501 `NOT_IMPLEMENTED` | у модели нет объяснений (baseline) |
| 503 `MODEL_NOT_READY` | модель не загрузилась |

## deps.py

Зависимости для маршрутов: `get_service` и `get_settings`. Сервис хранится в `app.state`, маршруты получают его через `Depends`, а не через глобальные переменные. Если модель не загрузилась, `get_service` сразу отвечает 503.

## predictor.py

Загрузка модели и прогноз. Приложение работает только через интерфейс `ForecastModel` (`kind`, `version`, `predict`, `info`, `explain`), поэтому модель можно заменить, не трогая API. Реализация выбирается полем `kind` в `config.json` папки модели:

- `TwoStageModel` (`two_stage`, по умолчанию): итоговая модель, обёртка над `src/forecaster.py`. `explain` по паре показывает вероятность и порог по неделям, сырое и целое количество и пять главных признаков по SHAP у классификатора и регрессора. SHAP считается по первой CatBoost-модели ансамбля, а вероятность и количество по всему ансамблю.
- `BaselineModel` (`baseline`): среднее за 8 недель, меньше 1 штуки ставится 0. Нужна, чтобы проверить подмену модели, и как запасной вариант.

Чтобы добавить свою модель, достаточно класса с этими методами и записи в `MODELS`.

## service.py

`ForecastService` связывает модель, проверку входа и хранилище. Ключ прогноза - sha256 от версии модели и обоих файлов: повторный POST с теми же данными отдаётся из хранилища без расчёта и совпадает байт в байт. Расчёт идёт под семафором, не больше `MAX_CONCURRENT_PREDICTIONS` одновременно на процесс, остальные запросы ждут: полный расчёт берёт до ~1 ГБ памяти. Время этапов (разбор, проверка, ожидание, прогноз) уходит в `Server-Timing`.

Почему так: в шаблоне из ТЗ прогноз лежит в памяти процесса. Тогда второй клиент затирает прогноз первого, при нескольких воркерах GET попадает в процесс без прогноза, а после рестарта всё пропадает. Здесь воркеры не хранят состояние, всё лежит в хранилище.

## store.py

Хранилище прогнозов в `CACHE_DIR`: CSV, метаданные в JSON и данные для `/explain` (pickle со сжатием). Каждый файл пишется во временный и атомарно переименовывается, CSV пишется последним: если он есть, прогноз записан целиком. Хранится `MAX_FORECASTS` последних прогнозов. Это файлы на одном хосте (том Docker); для нескольких хостов здесь нужно общее хранилище вроде S3 или Redis, остальной код не меняется.

## validators.py

Проверки входа по разделу 10.4 ТЗ: пустой файл и не CSV (400); нет колонок, даты не в формате `YYYY-MM-DD`, история меньше 180 дней, `quantity` не число или отрицательное, `stock` не число (422). Все найденные проблемы собираются в один ответ. Отрицательный остаток не ошибка, это резерв. Товар в `stock` может называться `char_article` (как в ТЗ) или `article` (как в выданных файлах).

## static/

`swagger-ui-bundle.js`, `swagger-ui.css` и `redoc.standalone.js` - чужие файлы для документации без интернета. `solution.html` - `notebooks/solution.ipynb` без кода, собирается командой `make solution-html`.
